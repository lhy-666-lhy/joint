10. 不得因一个可选分支失败而阻塞无依赖的分支。特别是 Cartesian/IK、Diffusion 和 DAgger 均不能阻塞 direct-qpos 主线。

## 1. 问题、方法主张与边界

### 1.1 最终问题

从当前可观测场景、机器人状态和 SAPIEN task metadata 出发，预测并执行能够抓取目标 link、保持接触并将铰链物体打开到规定角度的动作。最终模型推理时不依赖 oracle 信息；目标 link 的真实打开角度只由 evaluator 用于停止。

### 1.2 两个核心主张

| Claim | 为什么重要 | 最低可信证据 | 对应实验块 |
|---|---|---|---|
| C1：在已抓稳的 operation-start 状态下，合适的 joint-space 模型与训练策略能够拟合 replay-qualified 轨迹并在闭环中打开物体 | 先证明动作学习本身，而不是让抓取或新 executor 掩盖问题 | 固定批量可记忆；训练 target 可重建；operation-only 闭环成功；三 seed、target-disjoint 结果优于强简单基线 | B1、B2 |
| C2：抓取轨迹直接预测与“目标抓取 qpose + 在线规划”应在同一合同下比较；affordance 应当通过改善可执行抓取和端到端任务成功发挥作用 | 最终任务必须包含抓取，且要知道应该学习整条路径还是只学习目标；还必须证明 affordance 对物理任务有实际贡献 | GT 和 learned 两级 qpath/qpose exact-paired 对比；predicted-affordance 相对 zero/no-affordance 提升 retention 或完整任务；联合模型提升完整任务且 operation 不退化 | B3、B4 |

### 1.3 必须排除的错误解释

- “轨迹来自 force/admittance controller，所以部署也必须重建该 controller。”错误。主线学习 replay-qualified joint command，而不是采集控制器内部状态。
- “offline loss 低就等于会开门。”错误。offline fit、预测轨迹重放和实时闭环必须分层报告。
- “更大的 Transformer 或 Diffusion 必然更好。”未证明。先比较参数和训练预算受控的确定性模型。
- “affordance IoU 更高就等于抓取和任务更好。”错误。affordance 必须通过下游 grasp 和完整任务评测。
- “一个 SE(3)/IK 分支失败说明模型方向失败。”错误。它只能否定该表示和转换链。

### 1.4 第一阶段明确缩小范围

第一阶段只做 operation-only：

```text
recorded operation-start robot/object state
    -> live observation + robot history + task metadata
    -> model predicts H x 9 joint targets
    -> canonical position drive executes K-step prefix
    -> re-observe until success or horizon
```

该阶段固定使用记录的 closed grasp state，因此不评估 grasp 泛化。operation winner 冻结后必须进入 grasp/affordance 和完整系统阶段，不能以 operation-only 作为最终交付。

## 6. 冻结执行与评测合同

### 6.1 Canonical qpos executor

```text
model output or reconstructed label
    -> denormalized absolute 9D joint target
    -> joint.set_drive_target / zero drive velocity target
    -> one SAPIEN physics step
```

固定参数来自 E1。所有 qpos 模型共享完全相同的 decoder-to-drive 路径。Cartesian 模型若以后触发，其 IK 属于该模型的一部分，不能再声称“所有模型共享同一 IK”。

### 6.2 Operation-only 起点与停止

- 每个 rollout 从该 trajectory 记录的 operation-start robot/object state 开始；不重放 approach/close。
- fingers 从 recorded closed state 开始，模型仍输出或保持显式 finger target。
- success：target joint normalized opening ratio `>=0.4`。
- stop：success、统一 source-operation horizon 上限或明确 safety failure。
- 真实 opening angle 不进入 model forward。
- 所有模型使用相同 episode order、initial state 和 evaluator seed。

### 6.3 四级“拟合”定义

| 层级 | 问题 | 必须报告 | 失败含义 |
|---|---|---|---|
| F0 adapter 回环 | 新 data adapter 是否保持原命令 | normalize/denormalize max error、chunk stitch equality、2 条 replay success | 数据/解码实现错误 |
| F1 固定批量记忆 | 模型和 optimizer 能否记住 64 个 chunk | loss curve、normalized MAE、per-dim MAE、reload parity | 模型/训练实现错误；不是任务困难 |
| F2 记录观测下预测轨迹 | 模型对数据分布内的预测是否达到物理可用精度 | first-step/endpoint/p95 error、预测轨迹 replay success | label loss 与物理敏感性不匹配，或容量/采样不足 |
| F3 live closed loop | 模型进入自己产生的状态后是否仍能完成操作 | target-macro success、progress、wrong-way、retention、latency | 状态分布偏移、观测或闭环策略问题 |

offline fit 可以证明“模型是否学到标签”，但不能替代 F3。反过来，F1 未通过时也不得跳到 F3 用 rollout 噪声解释模型。

### 6.4 指标

主任务指标：

- target-macro operation success；
- episode-micro success；
- exact-paired success difference；
- target-bootstrap 95% CI；
- normalized signed progress。

拟合指标：

- normalized和denormalized action MAE；
- arm/finger 分开报告；
- first executed action MAE；
- chunk endpoint MAE；
- per-horizon p50/p95 error；
- command delta/smoothness error；
- repeat-last-command 和 train-mean baseline 的相对改善；
- train/CAL gap。

机制指标：bilateral contact、retention、wrong-way、invalid/nonfinite、operation horizon、inference latency。任何 contact composite 都不能覆盖已经达到 0.4 的 task success。

## 7. Operation 模型与训练策略

### 7.1 共享输入与 encoder

三个核心模型都使用：

- live 1024-point XYZ + target-link mask；
- frozen ZERO affordance channel（core architecture comparison；见7.4）；
- 4-step actual qpos/qvel history；
- last command、finger state、contact/mask；
- target link metadata、hinge axis、joint limits、open direction；
- 同一 `PointCloudContextEncoder`，hidden dimension 256。

target-link mask 必须由已允许的 target-link identity 与当前 SAPIEN 3.0 segmentation render确定性对齐生成；它可以随当前观测更新，但不得从trajectory sidecar、GT grasp、future state或outcome读取。该生成方式及entity/link ID映射必须进入forbidden-field audit。

Architecture 6 recorded source NPZ 不含 robot qvel。自 revision `A6-INPUT-v1.1` 起，固定批量和离线训练的 causal qvel proxy 冻结为 `240 * (actual_joint_qpos[t] - actual_joint_qpos[t-1])`，首个可用历史点的 previous index 向前 clamp；240 Hz 来自 canonical SAPIEN scene timestep `1/240 s`。live forward 仍读取 SAPIEN 当前 actual qvel，不用 finite difference 覆盖 live state。该差异必须作为 `qvel_source` 输入 lineage 持久化，并在首次 live producer sanity 中检查单位、shape 与 finite，不得读取未来 qpos。

共享 state/context schema 同时冻结：4-step qpos/qvel 为72维，last 9D command为9维；当前 `contact_feedback` 33维加1维 availability mask；task metadata 为 target joint type one-hot、active-joint ordinal、URDF local hinge/slide axis、joint lower/upper 与 open direction `+1`。finger state/command 已分别包含在9D qpos与command中。target mask 作为每点第4个输入通道；ZERO affordance 是独立全零通道，不与target mask混用。固定批量若无法从source/URDF无outcome地生成上述字段，保持训练阻塞。

首轮 encoder 使用同一初始化和训练状态。decoder 参数量尽量控制在 `+/-20%`，无法匹配时必须报告参数量和 latency，不能隐藏。

### 7.2 三个核心架构

| System | Decoder | 目的 | 主线地位 |
|---|---|---|---|
| `O-MLP-ABS` | pooled scene/state feature -> MLP -> flattened `32x9` | 最简单容量基线，暴露 Transformer 是否必要 | MUST |
| `O-PAR-ABS` | ACT-like learned queries，parallel Transformer decoder | 强确定性 chunk baseline，可复用 Architecture 2 | MUST |
| `O-CAUSAL-ABS` | causal Transformer，训练时 teacher forcing，推理自回归生成 chunk | 检验显式 action dependency 是否有用 | MUST |

无训练基线 `repeat-last-command` 和 `train-mean-chunk` 必须与三者同时报告，但不计入三个 model family。

### 7.3 冻结首轮训练配置

- optimizer：AdamW；
- learning rate：`1e-4`；weight decay：`1e-6`；
- 有效 batch size：每个 optimizer step 固定 64 samples；单卡 microbatch 由第14.1节 resource pilot 在 64 的整除数中选择，用 gradient accumulation 保持有效 batch=64；
- formal DYN64 screen：6,000 optimizer steps；
- checkpoints：500、1,500、3,000、6,000，仅固定 6,000-step checkpoint 参加 model comparison；
- dropout：0.1；
- point augmentation：三个模型完全相同；固定批量记忆时关闭 augmentation；
- loss：valid-mask normalized per-dimension L1，arm/finger 等维归一化；首轮不加 endpoint、smoothness 或 outcome loss；
- seed：fixed-batch `20260805`；formal seeds `20260805/20260806/20260807`；
- 不按 outcome 选 checkpoint 或 best seed。

若某架构不能通过固定批量，允许修复实现；不允许为它单独搜索一组正式超参数。实现有效但 6,000 steps 仍不拟合时，该架构形成 scoped training-fit negative，其他架构继续。

### 7.4 Affordance 在 operation 阶段的使用

三个operation架构的O010-O210 core comparison统一使用ZERO channel，以隔离decoder/action representation/training strategy，不让旧split checkpoint或affordance质量改变架构排名。A000-A030可与O010-O140并行，但不阻塞ZERO主线。

正式PRED由下列固定流程产生：

1. `A6-A000`：按5.5建立A5_TRAIN/A5_CAL affordance manifests，禁止旧split membership；
2. `A6-A010`：8个A5_TRAIN source rows固定批量记忆，augmentation关闭，2,000 steps；pointwise MAE`<=0.02`、非退化row AUPRC`>=0.95`、finite/nonzero gradients、strict reload max error`<=1e-6`；
3. `A6-A020`：三个seed `20260805/06/07`从同一合法初始化训练Point-M2AE dual-head updated label；uniform combined views、1024 points、100 epochs x 70 steps、batch96、AdamW lr`4e-4`、warmup10、CE:Dice:MSE=`1:1:10`、rotation30deg、jitter0.005、no mirror/dropout；固定使用step7,000 `last.pth`，不在训练中读取CAL；
4. `A6-A030`：三个last checkpoints在A5_CAL primary views只读评估IoU@0.05/AUPRC/MAE，并在DYN8做live 1024-point forward；冻结与训练一致的`pc_normalize`、input point order和per-point score回贴，要求output `[B,1024]` finite、reload/live重复max error`<=1e-6`、zero point reorder。全部checkpoint冻结、不选best epoch/seed；离线IoU低不阻塞ZERO主线。

O220只对O200/O210及任何已触发O230/O240后冻结的唯一operation配置做三臂干预：

1. `O-AFF-ZERO`：affordance channel 全零；
2. `O-AFF-PRED`：A030 split-safe frozen predicted map，single-seed screen按同seed配对；
3. `O-AFF-GT`：GT map，仅作上限，不可部署。

O220 的三臂是三份matched training：相同初始化hash、样本、seed、optimizer、steps和checkpoint rule，只改变train/eval时affordance channel来源；不是把一个PRED-trained checkpoint仅在test时换输入。另对冻结的O-AFF-PRED checkpoint做一次`PRED -> ZERO/GT`输入替换，只报告consumer sensitivity，不用于选模型或声称GT上限。若PRED晋级，O300三个action seeds分别配对同seed A030 checkpoint，不做跨seed组合或挑选。

判定：

- PRED 优于 ZERO：保留 affordance operation conditioning；
- GT 优于 PRED、PRED 约等于 ZERO：瓶颈在 affordance predictor；进入 B3 专项；
- GT 也不优于 ZERO：operation 模型不再强制使用 affordance，affordance 只用于 grasp proposal/ranking；
- 不允许只用 affordance IoU 决定上述 routing。

若O-AFF-PRED相对ZERO的task绝对差异`>=5pp`且O140有第二个存活decoder，则触发`A6-O225`：在相同PRED输入、seed、budget下重训/评测runner-up decoder。只有O225能改变decoder winner；否则O220只决定winner decoder的affordance gate。该交互检查不读取MECHDEV/final。

### 7.5 Action representation 与训练策略优先级

只有三架构 absolute screen 产生唯一胜出 decoder 后，依次运行：

1. `absolute` vs `start_delta`：同一模型、样本、seed、budget；`start_delta = target command - current actual qpos`，解码后仍是 absolute q target。
2. target/trajectory/motion-balanced sampling vs raw-tick-uniform sampling：验证“低 loss 来自静止占比”这一反解释。
3. endpoint-weighted loss：仅当 first-step 精度好而 endpoint/predicted-replay 失败时触发。
4. scheduled sampling：仅当 F2 通过而 F3 明显失败，并由 trace 证明 action-prefix/state distribution shift 时触发。
5. DAgger：只有 scheduled sampling 仍失败且存在 train-only、无 test outcome 的合法 teacher 时才允许新 revision。

Diffusion 不是默认模型。只有相同/近邻 deployable observation 在 `A5_TRAIN` 中对应稳定、分离的多个 action mode，且确定性 winner 表现为 mode averaging 时，才授权 equal-input/equal-output Diffusion 对照。否则保持确定性模型。

### B1 Gate

1. `A6-D010` adapter roundtrip：两条 fixed-gate trajectory 的 normalize/denormalize 和 stitch max abs error `<=1e-6`；通过同一 executor 后 success 与原 replay 一致。

## 10. Experiment Block B3：抓取与 affordance

operation winner 冻结后开始；B3 不允许改 operation checkpoint。

### 10.1 抓取问题定义

输入是 initial live point cloud、target-link mask、robot state 和 task metadata。输出不是 test outcome，而是抓取 qpath 或目标抓取 qpose。执行顺序固定为 approach -> close -> settle；随后接 B2 frozen operation winner。

每个 observation group 只能聚合同一 initial robot/object/base/camera state、同一 target link 下的 trajectory-specific labels。禁止仅按 target key 把不同初始状态的 qpath 混成一个 set。首轮每组固定最多 K=4 candidates，少于 4 时使用 candidate-valid mask，不复制标签填充。

必须先比较两个 GT 接口上限，再训练模型：

1. `G-ORACLE-TRAJ`：直接执行对应 trajectory 的 stored `grasp_plan_qpath`；
2. `G-ORACLE-QPOSE`：只读取 G000 从同一 teacher lineage 预先物化并hash冻结的 `q_path_terminal_open` sidecar，从当前7D robot state在线运行joint-space Curobo planner得到qpath；该 evaluator/consumer禁止读取stored qpath、stored/GT pregrasp或SE(3) frame。sidecar producer可以在G000离线验证`q_path_terminal_open == grasp_plan_qpath[-1]`，但producer与consumer必须分离。

两者共享同一 target lock、planned-qpath scheduler、finger-open approach 和固定 `hold-open/close/settle=30/80/120` physics ticks。随后接相同 frozen operation winner。该 oracle pair 只量化“保留完整路径”和“只保留目标 qpose 后重新规划”的接口差异；不参与 deployable winner。

为排除 planner waypoint 数量造成的执行时长混淆，G005 的 stored path 与 fresh planned path都先保留首尾点并按7D累计弧长确定性重采样到 `L=64`，再使用相同的 `execute_curobo_qpath` 参数。必须同时保存 raw path 与 executed L64 path；重采样只能沿原折线插值，不能平滑、重规划或改变endpoint。

主指标：

- planner/reach success；
- collision/joint-limit-valid qpath coverage；
- terminal qpose error 和 path tracking error；
- bilateral contact；
- settle-window retention；
- operation entry；
- 完整 task success。

offline qpose/frame error 只作诊断。

### 10.2 两个核心抓取表示

| System | 描述 | 用途 |
|---|---|---|
| `G-TRAJ` | shared encoder 直接预测 K=4 条 grasp arm qpath；每条 stored teacher 按7D累计弧长确定性重采样为L=64，输出相对当前arm qpos的`Kx64x7`，decode后恢复absolute qpath；执行前只做finite/joint-limit/collision validation，不调用planner修路径 | 检验完整路径几何是否必须由模型保留 |
| `G-QPOSE` | shared encoder 预测 K=4 个相对当前arm qpos的 `q_path_terminal_open` targets，decode为absolute 7D qpose；每个target从**当前7D state**调用single-segment online joint-space planner生成路径 | 检验只学习目标、让planner负责路径是否更容易泛化 |

两个系统使用同一observation encoder、K、训练observation groups、ZERO-affordance channel、训练exposure、seed、close/settle、path executor和frozen operation winner。current-relative 7D target使用同一只在A5_TRAIN拟合的per-joint normalizer。decoder参数量尽量控制在`+/-20%`；无法匹配时报告参数量、planner time和端到端latency。

每个head输出K=4个proposal和K个`presence_logit`。G000只允许每个observation group内最多4个同initial-state、同target-link、trajectory-specific labels；少于4个时不复制label。Hungarian matching只在该group的合法labels和4个predictions间进行；matched proposal的presence target为1，unmatched为0。presence只监督“该slot是否对应数据中的proposal”，不是成功率、outcome confidence或ranker。

冻结loss如下：`G-TRAJ` matching cost/training geometry loss为`1.0 * mean_waypoint_L1 + 1.0 * endpoint_L1 + 0.1 * first_difference_L1`，其中finite difference与teacher差分比较，不能用趋零smoothness；`G-QPOSE` geometry loss为`1.0 * terminal_L1`；两者都加`0.1 * presence_BCE`。所有L1在shared normalized 7D空间计算，valid-label mask后按实际label数归一化，不读取contact/task outcome。

推理时先使用冻结阈值`sigmoid(presence_logit) >= 0.5`，再做finite/joint-limit/collision/path合同过滤；无候选通过即记为`no_executable_grasp_proposal`，禁止用GT或top-outcome fallback。两条route均将最终path按相同累计弧长规则重采样到L=64并走同一executor；G-QPOSE的planner raw path只允许折线重采样，G-TRAJ禁止planner修正。剩余合法路径统一调用`select_shortest_joint_path`，tie按model input order。

`G-QPOSE` 绝对禁止沿用 Architecture 2 evaluator 中“predicted qpose + GT pregrasp”的旧 override 方式。Architecture 6 必须提供 current-state -> predicted-qpose 的单段 joint planner adapter，并为“未读取 stored pregrasp/qpath”写 AST/field audit。

### 10.3 Affordance 与抓取 head

在`G-TRAJ`和`G-QPOSE`的learned exact-paired representation comparison中，二者都先使用ZERO channel，以保证唯一主变量是“完整qpath vs terminal qpose + planner”。表示winner冻结后才运行：

| System | 描述 | 用途 |
|---|---|---|
| `G-WIN-ZERO` | winner interface，affordance channel全零 | no-affordance基线 |
| `G-WIN-PRED` | winner interface，A030同seedsplit-safe predicted affordance | deployable candidate |
| `G-WIN-GT` | winner interface，GT affordance | perception upper bound |
| `G-JOINT-AFF` | winner interface + shared encoder同时预测稳定 affordance heatmap和grasp output | 联合监督候选 |

GT affordance 和 GT trajectory/qpose 只作 ceiling。最终系统只能使用 predicted affordance或无affordance。

### 10.4 标签与 loss

- affordance head 优先学习可由几何解释的稳定 label；不要求 geometry-only heatmap解释 replay/controller-dependent outcome。
- trajectory/qpose labels严格来自每条 trajectory 自己的 `grasp_plan_qpath`；路径和terminal target不得跨trajectory拼接。
- 后续可选 candidate heads 分开预测 reach、bilateral contact、retention、operation progress/task success；首轮representation comparison不使用这些 outcome heads。
- 只有 shortest-valid baseline和GT outcome headroom显示至少5pp可利用空间后，才允许训练ranker；test 时不得读取真实 outcome。
- `q_path_terminal_open` 是 grasp goal teacher；`q_operation_start_closed` 只作 close/settle compatibility observation。

### 10.5 轨迹预测与 qpose+planner 决策门

1. GT pair 必须先完成相同 CAL episodes 的 exact-paired 报告。`GT-TRAJ`要求path合同100%、task success>=90%；`GT-QPOSE`要求zero stored pregrasp/qpath read、planner/terminal合同coverage>=90%，且task success>=80%或与GT-TRAJ差距<=15pp。未通过只停止对应learned route，不阻塞另一接口；两者差值是新结果，不能套用P010/QF010结论。
2. fixed-batch：两条 learned route 都必须记住相同8 observation groups；2,000 steps、augmentation关闭；G-TRAJ matched normalized path/endpoint MAE均`<=1e-3`，G-QPOSE matched normalized terminal MAE`<=1e-3`，两者geometry loss至少下降100x、presence分类100%、finite/nonzero gradient、strict reload output max error`<=1e-6`。任一项失败先归为implementation/training-fit问题，不运行physics。
3. DYN64 learned comparison必须使用同一 observation、affordance、K、seed和operation winner；task success是主指标，planner coverage、path validity、retention和latency解释差异。
4. 若一方相对另一方完整task point estimate `>=5pp`且target-bootstrap CI lower bound >0，选该表示。
5. 若差值不足5pp或CI跨0，不声明科学winner；为继续完整系统，按预注册工程顺序选择：先较低`no_executable_grasp_proposal`率，再较高retention，再较低p95端到端latency，最后较少runtime依赖。每层只有差异超过其bootstrap/measurement noise才进入下一层，选择理由必须写入G120。
6. 不允许只按offline path/qpose loss选择winner。
7. 若G005只放行一条route，G030-G110只训练和评测该存活route；G120将其冻结为工程入口，但必须写`representation_comparison_not_run`，不得声称其优于被oracle gate阻止的route。

### 10.6 Affordance 决策门

先运行同模型同预算的 `ZERO/PRED/GT`：

G130同样是三份matched training：初始化hash、observation groups、seed、optimizer、steps、K、representation和checkpoint rule完全相同，只改变train/eval的affordance channel来源；PRED必须来自A030同seedcheckpoint。另对冻结G-WIN-PRED checkpoint做一次`PRED -> ZERO/GT`输入替换，作为“模型是否消费该channel”的敏感性诊断；matched-training结果裁决utility，输入替换结果不能替代它。若PRED晋级，G200三个grasp seeds分别配对同seed A030 checkpoint，不做跨seed组合或挑选。

- PRED 相对 ZERO 的 grasp retention 或完整 task success point estimate `>=5pp` 且 CI lower bound > 0：证明 predicted affordance 有用；
- GT 明显优于 PRED：允许优化 affordance label/model，但不改变 grasp/operation；
- GT 与 ZERO 无差异：停止把 affordance 作为该 consumer 的输入，不继续调 Stage 1；
- 任何结果必须同时报告 point-level IoU/AUPRC 和下游 task，task 为最终裁决。

路由：只有`PRED > ZERO`或`GT > ZERO`显示下游utility/headroom时才运行G140/G150；否则将G140/G150记为`NOT_APPLICABLE_BY_GATE`，冻结G-WIN-ZERO并直接进入G200。可选affordance分支不得阻塞grasp或完整系统。

若G-WIN-PRED相对ZERO的task绝对差异`>=5pp`、且G005放行了两条representation route，则触发`A6-G135`：在相同PRED输入、seed、budget下训练/评测G120未选中的另一representation。只有G135可因representation-affordance interaction改写G120工程winner；否则G130只决定winner representation的affordance gate。

- **Priority**：MUST-RUN。

## 11. Experiment Block B4：抓取、affordance 与 operation 联合优化

### 11.1 顺序

1. `J-FROZEN`：冻结的operation module（含O220选出的ZERO/PRED gate）+ grasp module（含G130/G150选出的ZERO/PRED gate），建立可部署串联系统；两个head的affordance gate独立，不强制相同。任何PRED gate都按seed index读取A030 checkpoint，禁止E11旧权重。
2. `J-SHARED`：共享live视觉encoder，至少联合监督`L_action + L_grasp`，并保持O220/G130冻结的per-head affordance gate。若两个head都选择ZERO，则不接affordance channel/loss；若任一head选择PRED但G-JOINT-AFF未晋级，则继续使用同seed frozen A030 map；只有G-JOINT-AFF晋级时才共同训练affordance head并加入`L_affordance`。各head保持独立，loss weight只用A5_TRAIN初始梯度范数一次性标定。
3. `J-TASK-FT`：只有 J-SHARED 的完整 task 仍受 candidate ranking/operation compatibility 限制时，才用 A5_TRAIN rollout 做 bounded fine-tune；不读 MECH_DEV/final outcome。

Formal complete-system comparison固定三个seed。`J-FROZEN`按相同seed index配对operation/grasp checkpoints（不做3x3 best-combination搜索）；`J-SHARED`使用同三个seed独立训练。若J-TASK-FT触发，则每个J-SHARED seed各自继续，不按CAL/MECHDEV挑seed。

### 11.2 防止联合训练退化

- 每轮同时评估 operation-only frozen-start 和完整任务。
- 相对 B2 operation winner，operation-only success 下降超过 2pp 则 joint run 不得晋级。
- 相对 J-FROZEN，完整 task success point estimate 至少提升 5pp 且 CI lower bound > 0 才声明联合优化有效。
- 若 J-SHARED 无提升，保留简单串联系统，不自动进入 RL/DAgger。
- 最终 checkpoint forward 必须通过 forbidden-field audit，确认没有 GT affordance、GT grasp、object qpos、future action 或 outcome。
- checkpoint lineage audit必须证明E11 SHA-256未出现在正式module ancestor中；A030、operation、grasp和joint checkpoints按seed index闭合。

- **Priority**：MUST-RUN；J-TASK-FT 为 CONDITIONAL。

## 12. Experiment Block B5：必要性与简化检查

以下均不能阻塞 B1-B4：

- Diffusion：只在第 7.5 节多模态 gate 通过后比较。
- Cartesian keypose/IK：只作为独立 system-level candidate；必须先在自己的 GT keypose adapter 上通过，不影响 qpos 结论。
- 更大 3D backbone：只有 frozen encoder 的 train/CAL 表征均成为瓶颈且 decoder 已通过 fixed-batch 时比较。
- DAgger/RL：只有明确 closed-loop state-distribution 证据且 train-only teacher 合法时新 revision。

任何复杂候选必须在相同数据 exposure、最终输入、output semantics 和 latency 报告下优于简单 winner，否则保留简单系统。

- **Priority**：NICE-TO-HAVE / CONDITIONAL。

条件 run ID 固定为：`A6-X010`（Diffusion）、`A6-X020`（Cartesian/IK）、`A6-X030`（DAgger）、`A6-X040`（larger 3D backbone）。它们只能在对应 trigger 和新的 timestamped planning revision 后运行，不能改变 B1-B4 的冻结合同。

| 观察 | 结论 | 唯一允许的下一步 |

| A010不能记忆8个affordance rows | affordance adapter/loss/init实现错误 | 检查label、point order、gradient和reload；不启动A020，ZERO主线继续 |
| A030 split-safe PRED离线质量低 | 当前affordance predictor/label受限 | 保留为PRED诊断或在O220/G130被ZERO淘汰；不得换回E11，不能阻塞ZERO主线 |
| 三模型固定批量都不能记忆 | label、mask、loss、optimizer 或 shared encoder bug | 检查 per-dim target、gradient、normalizer；不得跑 physics sweep |
| MLP 通过而某 Transformer 不通过 | 该架构实现/优化失败 | 修该分支一次；其他通过分支继续 |
| fixed-batch 通过但 DYN64 train fit 差 | sampling、容量或 observation-label ambiguity | 先对比 repeat baseline、per-target conflict；再决定 representation/loss |
| offline 好但 predicted trajectory replay 差 | denormalized error、endpoint或chunk stitch 对物理不够精确 | 触发 endpoint/motion loss单变量实验 |
| predicted replay 好但 live closed loop 差 | exposure/state distribution shift | 触发 scheduled sampling；不换 executor |
| train closed-loop 好、CAL差 | 泛化不足 | 比较输入/regularization；不读 MECH_DEV |
| operation-only 好、完整任务差 | grasp/affordance/integration bottleneck | 进入 B3 stage metrics；不改 operation winner |
| GT direct qpath成功、GT qpose+planner失败 | target-only接口丢失必要路径/approach信息，或单段planner不足 | 停止G-QPOSE learned route；继续G-TRAJ，不修改operation |
| 两个 GT 接口都未达到 G005 route gate | 新 adapter/retiming/executor 或 grasp label contract 仍有问题 | 先审计 sidecar、current-state 起点、L64 retiming 和 telemetry；不得训练、不得写“抓取方向失败” |
| GT qpose+planner成功、learned qpose planner coverage低 | qpose prediction不在可规划流形 | 分析qpose error/limit/碰撞；只优化G-QPOSE representation，不改planner或G-TRAJ |
| G-TRAJ offline fit好但collision/path-invalid高 | trajectory loss没有约束可执行路径 | 触发单一collision/smoothness约束修复；不让planner重写预测路径 |
| G-TRAJ与G-QPOSE任务相当 | 没有证据支持任一表示在任务上更优 | 按10.5的预注册工程tie-break选完整系统入口，不写模型优劣claim |
| GT affordance 好、predicted差 | affordance predictor/label bottleneck | 只优化 affordance branch |
| GT affordance也无收益 | consumer 不需要 affordance | 删除该 consumer 的 affordance 输入，保留抓取 proposal 作用 |
| frozen pipeline 好、joint training差 | negative transfer | 保留 frozen pipeline，拒绝 joint branch |

只有当三个核心 operation family、抓取三臂以及 frozen/joint integration 都在合同有效、训练 fit 已通过的情况下失败，才允许讨论目标是否受数据可辨识性限制；仍不得写笼统的“所有方向 exhausted”。

### 14.1 资源预检、并行度冻结与 GPUALIVE

资源调整只优化吞吐，不得暗中改变科学合同。每种新 workload 在首个正式 run 前必须做一次短 resource pilot；同一 workload 的后续 seed 直接复用已冻结设置。`workload_signature` 至少包含 task/run family、model/encoder、input/output shape、precision、dataset/backend、renderer/planner、hardware GPU/CPU 型号和 software environment hash。任一项改变才重做 pilot。pilot 只读 TRAIN 或合成 fixed batch，不读 CAL/MECH_DEV/final outcome，不用 pilot 结果选模型。

**CPU-only/render/materialization 任务：**

1. worker 从 `1 -> 2 -> 4 -> 8 -> ...` 几何增长，上限为当前可用 logical CPU 数和内存安全上限；每档用相同 input shard、warmup 和至少 60 s 稳态窗口。
2. 记录 samples/frames/episodes per second、wall time、CPU mean/p95、RSS/peak memory、I/O wait、失败/重试数。选择吞吐最高且稳定的档位，不以 worker 数或 CPU 占用率本身作为目标。
3. 出现任一条即停止向上试探：相邻档吞吐改善 `<10%`；可用 CPU 持续达到 `>=80%`；I/O wait 或内存/交换成为明确瓶颈；出现 OOM、renderer 不稳定或吞吐回退。回退到上一个稳定档位。
4. E9 已证明的同签名 DYN64/materialization 直接冻结 2 workers；不得为了“吃满 CPU”重复试验已知的吞吐平台。

**GPU training/inference 任务：**

1. resource pilot 开始前停止 pilot 所用 GPU 上的 GPUALIVE，并确认其 CUDA context 已退出。先固定最小可行 microbatch，按 `0/1 -> 2 -> 4 -> 8 -> ...` 探测 DataLoader/CPU workers；再冻结 loader workers，按有效 batch 的整除数递增 microbatch。每档至少 warmup 20 steps，再计时 60 s 或 100 steps（取较长者）。
2. operation/grasp 首轮比较始终保持 effective batch `64`；A020 始终保持 effective batch `96`；其他 run 以对应预注册值为准。`effective_batch = microbatch_per_device * world_size * gradient_accumulation_steps`。比较臂之间还必须冻结 optimizer steps、sample exposure、learning-rate semantics、seed 和 checkpoint rule。
3. 每档记录 training samples/s、optimizer steps/s、mean/p95 step time、GPU SM mean/p95、peak memory、CPU/RSS/I/O wait、OOM/retry。选择稳定吞吐最高且 peak GPU memory `<=80%` 的档位。出现 OOM/nonfinite、超过内存上限、相邻档吞吐改善 `<10%` 或吞吐回退即停止向上试探，OOM 后回退至上一个稳定档，不得降低有效 batch 改变对比。
4. 若在有效 batch、内存安全和数据供给约束下无法达到高 GPU utilization，将任务标记为 CPU/IO/renderer/planner/small-model bound，不得通过改变 H/K、模型、有效 batch 或数据采样来伪造高占用率。优先在其他 GPU 并行独立 seed/config job。
5. 8-GPU 机器的调度优先级为：多个独立单 GPU job > 在空闲卡上开启后续已解锁 job > DDP。只有当没有可并行的独立 run，且 matched pilot 证明 DDP 的总 samples/s 至少提高 10%，才允许 DDP；仍须保持相同有效 batch 和 sample exposure。

**GPUALIVE 生命周期：**

- Codex 分析、CPU-only 任务、等待外部 artifact、两个 run 的空档以及逻辑循环 stopped 时，只要卡上没有真实 GPU 工作负责的 CUDA process，必须 ensure 唯一 GPUALIVE session 运行；已有 session 时禁止重复启动。
- 仅部分 GPU 被真实任务使用时，GPUALIVE 只能使用无实验 CUDA process 的空闲卡。低利用率真实任务仍“拥有”其 GPU；不得在同一张卡上叠加 GPUALIVE 扭曲吞吐、显存或稳定性。
- 真实 GPU resource pilot/formal run 进入 `launching` 前，必须停止其将使用的 keepalive context；真实任务产生 terminal artifact、crash 或释放 GPU 后，立即在无占用卡上恢复 GPUALIVE。
- GPUALIVE 只是资源保活基础设施。它的 PID、tmux session、GPU utilization 或持续运行绝不是实验进度、成功或完成证据。

每次 pilot 作为对应正式 run 的子 artifact，使用 `<run_id>-RP`，不新增科学 run ID。必须保存 `resource_pilot.json`：`workload_signature`、硬件/环境 hash、候选 workers/microbatch/world-size/accumulation、每档测量、选定值、停止原因、瓶颈分类、有效 batch/sample-exposure parity 和 GPUALIVE stop/restore 记录。资源预检不改变 run gate，也不能作为扩大训练预算的理由。

## 17. Planning revision 规则

以下情况允许直接修实现并使用新 run ID：

- Python/CUDA/serialization/launcher crash；
- hash consumer、field bookkeeping、relative-path 或 completion predicate bug；
- 修复后 model、data、seed、budget、metrics 和 scientific gate 完全不变。

以下情况必须先修改本计划并生成 timestamped revision：

- 改 action representation、H/K、input schema、split、executor、loss、optimizer、training steps；
- 新增 Diffusion、Cartesian、DAgger、RL 或新 candidate generator；
- 修改 success threshold/horizon；
- 使用新的 oracle 字段；
- 在已读 MECH_DEV/final outcome 后提出新候选。

在有效 batch、optimizer semantics、steps、sample exposure、seed、数据和模型均不变的前提下，调整 DataLoader/CPU workers、microbatch/gradient accumulation 分解、独立 job 并发度或经第14.1节证明的 DDP 不算科学合同 revision；但必须先落盘 resource pilot 并在所有对比臂中保持公平。改变有效 batch 或 sample exposure 仍必须新 planning revision。

revision 必须同时更新 fixed-name plan 和 tracker。不得只在实验脚本或对话中改变合同。
